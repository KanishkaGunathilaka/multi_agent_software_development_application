# User Stories

**User Stories**

| # | User Story | Acceptance Criteria | Definition of Done | Priority |
|---|------------|---------------------|--------------------|----------|
| 1 | **As a developer, I want a scaffolded Node‑JS Express project, so that the team can start building the authentication API immediately.** | • A new repository (or project folder) is created with `package.json`.<br>• Express is installed and a basic server (`app.js` / `server.js`) runs on a configurable port.<br>• ESLint (or equivalent) and Prettier are set up with CI‑friendly scripts.<br>• Environment‑variable handling (`dotenv`) is configured for `PORT`, `JWT_SECRET`, and DB connection strings.<br>• A `README.md` contains project description, setup steps, and how to run tests. | • Code is pushed to the main branch.<br>• All linting and formatting scripts run cleanly.<br>• `npm start` starts the server without errors.<br>• Unit‑test placeholder files exist and the test command exits with success. | High |
| 2 | **As a new user, I want to register with an email and password, so that I can obtain an account in the system.** | • `POST /api/auth/register` accepts `email` and `password` (JSON body).<br>• Email must be a valid format and not already taken.<br>• Password must meet a minimum strength rule (e.g., ≥8 chars, includes numbers/letters).<br>• Password is hashed using a strong algorithm (e.g., bcrypt) before storage.<br>• On success, the API returns **201 Created** with a JSON payload containing the newly created user’s ID and a JWT access token.<br>• Sensitive fields (password hash) are never returned. | • Endpoint implemented in Express router.<br>• Model/schema for `User` exists (abstracted DB layer).<br>• Password hashing and email uniqueness validation are covered by unit/integration tests.<br>• API documentation (Swagger/OpenAPI) includes the endpoint definition.<br>• All tests pass (`npm test`). | High |
| 3 | **As a registered user, I want to log in with my email and password, so that I receive a JWT to authenticate subsequent requests.** | • `POST /api/auth/login` accepts `email` and `password` (JSON).<br>• Credentials are validated against stored user data.<br>• On success, returns **200 OK** with a JSON payload containing:<br> ‑ `accessToken` (JWT signed with `JWT_SECRET`).<br> ‑ `expiresIn` (seconds until expiration).<br>• The JWT payload includes user ID and any required claims (e.g., `role`).<br>• On failure, returns **401 Unauthorized** with an error message (no hint about which field is wrong). | • Login endpoint implemented and integrated with the user model.<br>• JWT generation uses `jsonwebtoken` and respects expiration configured via env variable.<br>• Tests cover successful login, invalid email, wrong password, and locked‑out scenarios (if applicable).<br>• Swagger docs updated.<br>• Code passes all linting and test suites. | High |
| 4 | **As the API, I need middleware that validates JWTs on protected routes, so that only authenticated users can access them.** | • Middleware extracts the token from the `Authorization: Bearer <token>` header.<br>• Token signature is verified with `JWT_SECRET`.<br>• Expired or malformed tokens result in **401 Unauthorized**.<br>• On success, `req.user` is populated with the decoded payload (e.g., `{ id, role }`).<br>• Middleware is reusable and can be applied to any route via `router.use(authMiddleware)`. | • Middleware module exists (`authMiddleware.js`).<br>• Unit tests verify handling of valid token, expired token, missing token, and tampered token.<br>• Example protected route (`GET /api/profile`) uses the middleware.<br>• Documentation notes required header format. | High |
| 5 | **As an authenticated user, I want to retrieve my profile data, so that I can view my personal information.** | • `GET /api/profile` is protected by the JWT middleware.<br>• Returns **200 OK** with a JSON object containing the user’s non‑sensitive fields (e.g., `id`, `email`, `createdAt`).<br>• If the token is invalid, the request is rejected by the middleware (401). | • Endpoint implemented and integrated with the middleware.<br>• Integration test covers successful retrieval and 401 on missing/invalid token.<br>• Response schema documented. | Medium |
| 6 | **As a client, I want to refresh my JWT before it expires, so that I can maintain a session without re‑entering credentials.** | • `POST /api/auth/refresh` accepts a valid **refresh token** (separate from access token) in the body or cookie.<br>• Refresh token is verified (signature, existence, not revoked).<br>• Returns a new access JWT and its expiry.<br>• Refresh token itself has a longer lifetime (configurable).<br>• Invalid/expired refresh token yields **401 Unauthorized**. | • Refresh‑token model/store implemented (e.g., DB table or in‑memory store).<br>• Endpoint created and covered by tests (happy path, revoked, expired).<br>• Security notes added to docs (httpOnly cookie recommendation). | Medium |
| 7 | **As a user, I want to log out, so that my refresh token is revoked and cannot be used again.** | • `POST /api/auth/logout` requires a valid refresh token (header or cookie).<br>• The token is removed/revoked from the store.<br>• Returns **200 OK** with a confirmation message.<br>• Subsequent attempts to use the same refresh token must fail with 401. | • Logout endpoint implemented.<br>• Tests verify token revocation and proper response.<br>• Documentation updated. | Low |
| 8 | **As a developer, I want comprehensive automated tests, so that future changes do not break authentication functionality.** | • Unit tests for each service/function (hashing, token generation, validation).<br>• Integration tests for the full request/response cycle on all auth endpoints.<br>• Test coverage ≥ 80 % for the `src/auth` directory.<br>• Tests run in CI pipeline and must pass on every push. | • Test suite located under `tests/` or `src/__tests__/`.<br>• Coverage report generated (`npm run coverage`).<br>• CI configuration (e.g., GitHub Actions) includes `npm test`. | High |

### Ambiguities / Missing Requirements (to be clarified)

| # | Ambiguity / Missing Detail | Suggested Clarification |
|---|---------------------------|--------------------------|
| A1 | **Persistence layer** – Which database should be used (MongoDB, PostgreSQL, MySQL, SQLite, etc.)? | Choose a DB or provide an abstraction so the team can plug in the preferred storage. |
| A2 | **User schema fields** – Apart from `email` and `password`, are there other required attributes (e.g., `firstName`, `lastName`, `role`, `isActive`)? | Define the full user model. |
| A3 | **Password policy** – Minimum length, required character sets, whether password history or breach checks are needed. | Specify exact validation rules. |
| A4 | **JWT claims & expiration** – What claims (role, permissions) must be embedded? What is the intended access‑token lifetime (e.g., 15 min, 1 h)? | Provide claim list and expiration config. |
| A5 | **Refresh token strategy** – Should refresh tokens be stored server‑side (DB, Redis) or be signed JWTs? How long should they live? | Decide storage mechanism and TTL. |
| A6 | **Logout handling** – Is token revocation required only for refresh tokens, or also for access tokens (e.g., blacklist)? | Clarify revocation scope. |
| A7 | **Rate limiting / Brute‑force protection** – Any requirements for throttling login attempts? | Define limits and response behavior. |
| A8 | **Error handling & response format** – Desired error payload structure (e.g., `{ error: { code, message } }`). | Standardize error contract. |
| A9 | **Environment & secret management** – Should secrets be loaded from `.env`, a secret manager, or injected at runtime? | Confirm secret handling approach. |
| A10 | **Documentation** – Is Swagger/OpenAPI required, or a separate markdown API spec? | Choose documentation format. |
| A11 | **Testing environment** – Should tests run against an in‑memory DB, mock, or a real test database? | Define test DB strategy. |
| A12 | **Internationalization / Localization** – Any multilingual error messages needed? | Determine i18n scope. |
| A13 | **Compliance / Security standards** – Any specific compliance (GDPR, OWASP) that must be adhered to? | List required standards. |

*These ambiguities should be resolved before implementation begins to avoid re‑work and ensure the delivered API meets all stakeholder expectations.*
